연구실 노트북(`~/ros2_ws/cam_lidar_recording/`)에서 본 수집과 가공을 할 때 확인할 것들.
2026-09-29 session_013 실험에서 나온 교훈을 정리했다.

## 1. 수집 전 — 이게 없으면 나중에 작업이 막힌다

| 항목 | 확인 방법 | 없으면 |
|---|---|---|
| **라이다 Phase Lock = Locked** | 위치 패킷(UDP 8308) 202 바이트. 0 Absent / 1 Sync / 2 Locked / 3 Error | 회전 시작 위상이 흘러 A안 지연값이 무의미해진다. session_013 은 Absent 였다 |
| **셔터 시각 로그** | MCU 기준 시각 + `N = FrameID + offset` 매핑 | B안 보정 불가. 2026-09-29 처럼 셔터 시각을 **가정**해야 한다 |
| **원시 pcap** (데이터 포트 2368) | `lidar.pcap` | ROS 헤더 시각은 노트북 수신 시각이라 점별 시각 계산에 못 쓴다 |
| **카메라 ↔ 방향 매핑 기록** | CAM1~4 가 각각 앞/우/뒤/좌 중 무엇인지 | 지연값을 어느 카메라에 줄지 정할 수 없다 |
| GPRMC 공급 | MAX3232 경유 | Phase Lock 의 '몇 시' 기준 |

### 카메라 지연값 확인

라이다는 회전 시작(0 ms)에 **앞**을 보고 시계 방향으로 돈다 — `0 ms 앞 → 25 ms 우 → 50 ms 뒤 → 75 ms 좌`
(session_013 실측). 따라서

- 우측 카메라 = +25 ms, 뒤 = +50 ms, 좌 = +75 ms
- **순서가 반대면 값도 반대**가 된다. 수집 전에 한 세션 찍어서 확인할 것.
- 노출이 8 ms 이므로 기준은 노출 **시작이 아니라 중간** (트리거 + 12.8 µs + 4 ms). 4 ms ≈ 2 cm.

## 2. 주행 방식

- **회전 구간을 반드시 포함.** 직선만 찍으면 보정 효과가 안 보인다. session_013 은 최대 16°/s 뿐이었다.
- **긴 직선 통로 주의.** 앞뒤를 구분할 특징이 없어 KISS-ICP 가 퇴화(degeneracy)할 수 있다. 기둥이 보이는 구간을 섞을 것.
- **오래 정지하지 말 것.** 정지가 길면 ICP 가 흔들린다.
- **세션 시작·끝에 5초씩 완전 정지.** ← 권장
  정지 상태는 모션 왜곡이 0 이므로, 그때 이미지와 점이 안 맞으면 **그건 캘리브레이션 오차**다.
  주행 구간과 비교하면 캘리브 오차와 시간 오차를 분리할 수 있다.

  | 구간 | 안 맞는 원인 |
  |---|---|
  | 정지 | 캘리브레이션 오차만 |
  | 주행 | 캘리브레이션 + 시간 오차 |

- 같은 구간 2회 이상 주행하면 재현성 확인, 출발점 복귀하면 드리프트 측정 가능.
- 지하주차장은 어둡다. 노출 8 ms + 빠른 속도 = 모션 블러 → 투영 검증이 어려워진다.

## 4. 노트북에서 실행 환경

`kiss-icp` 는 파이썬 3.12 이하 권장 (3.14 용 휠 없음).

```bash
python3.12 -m venv ~/venv_kiss
~/venv_kiss/bin/pip install kiss-icp==1.3.0 numpy scipy matplotlib
```

한글 그림 라벨이 깨지면 `plot_results.py` 의 `font.family` 를 리눅스 폰트로 바꾼다
(`NanumGothic` 등). 설치: `sudo apt install fonts-nanum`.

## 5. 가공 실행 순서

```bash
cd 포인트보정/code
S=../data/session_XXX/lidar.pcap
R=../results/session_XXX

# 1) 오도메트리 (deskew 켬 / 끔)
python3 run_kiss_icp.py $S -o $R/deskew_on
python3 run_kiss_icp.py $S --no-deskew -o $R/deskew_off

# 2) 점검 — 속도·회전·지도 정합 오차·KISS-ICP 와의 일치
python3 analyze_deskew.py $S --poses $R/deskew_on

# 3) 그림
python3 plot_results.py $S --on $R/deskew_on --off $R/deskew_off -o $R/figures

# 4) 카메라 셔터 시각 기준 보정 → 카메라별 포인트클라우드
python3 deskew_to_shutter.py $S --poses $R/deskew_on -o $R/shutter --save
```

> **실제 셔터 시각이 있으면** `deskew_to_shutter.py` 의 `CAMERAS` 상수
> (이름, 셔터 ms, 시야 중심 방위각) 를 로그 값으로 바꾼다. 지금은 A안 가정값이다.

## 6. 결과가 이상할 때

| 증상 | 원인 | 대응 |
|---|---|---|
| 이동 거리가 실제와 크게 다름 | KISS-ICP 퇴화 (긴 통로, 특징 부족) | 구간을 나눠 돌리기, `--max-range` 조정, LeGO-LOAM 등 특징 기반 검토 |
| 궤적이 튀거나 끊김 | 정지 구간, 급회전, 스캔 반 토막 | `vlp16_dataset.py` 의 `min_points` 상향 |
| 지도 정합 오차가 보정 후 더 커짐 | 자세가 틀림 | 자세부터 의심. 보정 코드가 아니라 Step 2 문제 |
| 앞 카메라만 오차가 큼 | 시야가 스캔 이음매에 걸림 | `gather()` 의 ±50 ms 창 확인 (이미 처리돼 있음) |
| 점이 이미지와 일정하게 밀림 | 캘리브 오차 또는 시각 기준 오류 | 정지 프레임으로 분리 확인 (2절) |
| Sophus `R is not orthogonal` | 텍스트 저장된 자세의 회전부 오차 | `orthonormalize()` 통과시킨 뒤 넘길 것 |

## 7. 가공 단계에서 판단할 것 (아직 안 정해짐)

- **클래스 정의** — 지면 / 벽 / 기둥 / 차량 / 보행자 / 라바콘에서 더 넣을지
- **정답(GT) 프레임 수** — mIoU·mAP 를 재려면 사람이 직접 라벨링한 기준이 있어야 한다
- **자동 라벨 방식** — 기하 기반(지면분리 → 클러스터링 → 박스 피팅)으로 초안을 만들고,
  클래스 구분은 카메라 YOLO 결과를 캘리브레이션으로 라이다에 옮기는 방법을 검토 중
  (※ 팀 확정 사항 아님. 6th Sprint 계획서에 적힌 2차 가공은 "객체탐지, 궤적생성, BEV View,
  PointCloud-Lidar Segmentation" 이다)
- 사전학습 세그멘테이션 모델은 **64채널 야외 학습 → 16채널 지하주차장** 이라 성능 저하 예상.
  쓰기 전에 실제로 돌려보고 판단할 것.
